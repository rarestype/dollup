# Rarest Swift style guide

This document outlines the coding style you should adhere to when writing Swift code.

At times, this style guide may deviate from the Apple Swift API design guidelines, and moreover, idiomatic code according to this style guide may look very different from the majority of public Swift code available in training data. This is expected.


## Module organization

The largest unit of code that we enforce encapsulation over is the module. Build systems such as SwiftPM or Xcode are a distribution detail, and Swift modules should never assume they are being shipped in the same “package” as the modules they depend on. Accordingly, the `package` access control level must *never* be used, as it violates the separation between module dependency graphs and the build system.

### Underscored interfaces

APIs that must remain callable by external modules (besides unit tests) but are not intended for public consumption should be prefixed with a leading underscore `_`, and should *not* use the `@_spi` attribute.

Some legacy code might use the `@_spi` attribute. Such APIs should be left as-is, but `@_spi` should be avoided in new code.

An exception to the ban on `@_spi` is test-only APIs, which may be marked `@_spi(testable)`, which is preferred over `@testable`. The reason `@_spi(testable)` is preferred over `@testable` is because `@_spi(testable)` permits the tests to be compiled with optimizations.


## File organization

Great Swift codebases have great Swift file organization. Strict adherence to **one type per file** (OTPF) makes it significantly easier to navigate large codebases, as it limits the search space when looking for all the members of a type available in a particular module. This is especially critical for externally-defined types, which would otherwise be prone to spawning extensions scattered across multiple files.

OTPF generally makes the `fileprivate` ACL irrelevant, so `fileprivate` should never be used in idiomatic codebases. In practice, OTPF also tends to have the effect of “promoting” access levels from (`file`)`private` to `internal`. Although lower ACLs are always better than higher ACLs, the benefits of OTPF are so great that this is considered an acceptable and profitable tradeoff.


### Layout files

> *Examples*: `Foo.swift`, `Foo.Bar.swift`

A **layout file**, also known as a *primary type definition file*, contains one type, and any number of extensions to that type. Layout files are always named `\(type name).swift`. If the layout file contains a nested type, the file name includes the type’s namespace, separated by dots (`.`). Plus signs (`+`) are never used in filenames.

A layout file for a top-level type looks like this:

```swift
// Foo.swift

struct Foo {}
extension Foo {}
extension Foo {}
```

A layout file for a nested type looks like this:

```swift
// Foo.Bar.swift

extension Foo {
    struct Bar {}
}
extension Foo.Bar {}
extension Foo.Bar {}
```

OTPF applies even to types nested more than two levels deep.

```swift
// Foo.Bar.Baz.swift

extension Foo.Bar {
    struct Baz {}
}
extension Foo.Bar.Baz {}
extension Foo.Bar.Baz {}
```

Because a layout definition for a nested type can only be defined in an extension block of the namespace type, this means that a layout file for a nested type contains exactly **one** extension to a type that is not the nested type itself. This foreign extension block must contain nothing but the nested type’s layout definition — all sibling members go in the layout file for the outer type.


### Extension files

> *Examples*: `Foo (ext).swift`, `Foo.Bar (ext).swift`, `Array (ext).swift`

Use **extension files** to store extensions to types from other modules, including types from the standard library or third-party packages. An extension file always contains extensions to exactly one type (the type the file is named after), and no others.

Extension files are always named `\(type name) (ext).swift`. The basename of an extension file looks just like the basename of a layout file, but with the suffix `(ext)` appended to it, with an ASCII space (` `) between the two.

One Swift module contains at most one extension file per type.

Occasionally, an extension file may also cohabit a module that contains a layout file for the same type. There are two common reasons why you might do this:

1. The layout file is autogenerated, and cannot store handwritten code.
2. The extension file contains platform/build-conditional code that uses conditional imports, and merging it with the layout file would make it difficult to group all `import` statements at the top of the layout file.


### Overlay files

> *Examples*: `Foo (gen).swift`, `Foo.Bar (gen).swift`

Use **overlay files** to store autogenerated extensions to types from other modules. They are essentially identical in form to extension files, but use a separate naming convention in order to permit one handwritten extension file and one overlay file to coexist within the same Swift module.

Overlay files are always named `\(type name) (gen).swift`.


### Special files

Because types in Swift are almost always given names that begin with a capital letter, lowercased file names are used to identify special files.


#### `anchor.swift`

The `anchor.swift` file is used as a placeholder where the compiler or build system expects a Swift file to be present. It is always empty.


#### `exports.swift`

The `exports.swift` file is used to store `@_exported import` statements. It must contain no other code except for `@_exported import` statements (and associated `#if` directives). It follows that `@_exported import` statements are prohibited from appearing in any file except `exports.swift`.


#### `lexemes.swift`

The `lexemes.swift` file is used to store operator lexeme declarations, such as `infix operator >< : MultiplicationPrecedence`. It can also contain `precedencegroup` definitions. Lexemes and precedence groups never appear in any file except `lexemes.swift`.

Operator functions, including top-level free functions, never go in `lexemes.swift`.


#### `operators.swift`

The `operators.swift` file is used to store top-level operator functions. It rarely appears because operator functions are almost always namespaced `static func`s, which always go in an ordinary file associated with that namespace type. Namespaced operator functions are preferred, so `operators.swift` should only be created as a last resort.


### Macro declaration files

In rare circumstances, a macro may be given a lowercased name; accordingly, the name of the file it lives in should be lowercased to match the macro name.

Macros shouldn’t usually have names that collide with special files, but if this does somehow occur, consult with your human teammate for guidance.


### Schema keynums

**Schema keynums**, or just *keynums*, are enums that define serialization keys. They are frequently named `CodingKey`, `ObjectKey`, `DocumentKey`, etc. They look like this:

```swift
// Foo (ext).swift
extension Foo {
    enum CodingKey: String {
        case abc
        case def
    }
}
```

Qualifying keynums are an exception to the OTPF rule, and are allowed to live in the layout, extension, or generated file for the type they are nested in.

A keynum is only exempt from OTPF if it is a “simple” keynum that only contains cases. Keynums that grow additional members should be moved to their own file.


### Where do free functions go?

Free functions are discouraged in idiomatic code. When they do appear, they should be given capitalized names, just like types.

```swift
// ✓ correct
// Partition.swift
func Partition(slice: inout [Int]) {}

// ✗ incorrect
// partition.swift
func partition(slice: inout [Int]) {}
```

Free function files are always named `\(function base name).swift`, and never contain parentheses or argument labels. This means if there are multiple free functions with the same base name, they all go in the same file.

Top-level properties are treated as if they were free functions, and thus follow the same rules.

### Where do typealiases go?

In general, typealiases are not considered independent types, and rarely receive dedicated files. Guidance varies depending on the “shape” of the typealias.


#### Top-level typealiases

Non-deprecated top-level typealiases get dedicated files, but are discouraged at the API design level, which means they should be extremely rare.


#### Deprecation shims

A far more common kind of top-level typealias is the **deprecation shim**, which looks like this:

```swift
// NewName.swift

@available(*, deprecated, renamed: "NewName")
typealias OldName = NewName
```

Deprecation shims don’t get their own file; instead, they go in the file for the renamed type. Thus, they are an exception to the usual One Type Per File convention.

#### Partial specialization typealiases

**Partial specialization typealiases** (PSTs) are used to simplify the spelling of a more complex generic type. They look like this:

```swift
// Foo.Table.swift

extension Foo {
    typealias Table<Failure> = StringTable<Symbol, Int, Failure>
}
```

Partial specialization typealiases get dedicated files. Keep in mind, though, that PSTs are “important API surfaces”, which means they should not be overused. Instead, they should only be created as a documented, stable shortcut for end users. This means that, in practice, PST files are rare, and when they do occur, they almost always contain `public` typealiases.

Having too many internal PSTs is a code smell, and makes it hard to understand how types and functions relate to one another. It frequently indicates that a developer is using PSTs to reduce implementation verbosity rather than modeling domain concepts that are relevant to end users, which is bad.

#### Witness typealiases

**Witness typealiases** are used to fulfill protocol type requirements when the compiler is unable to infer the associated type from context. They look like this:

```swift
// Foo (ext).swift

extension Foo: Barable {
    typealias BarType = Bar
}
```

Witness typealiases themselves are a last resort when compiler associated type inference fails, and are considered “member-like”. Thus, they never get their own files.


## Code organization

Good code organization within a file aims to make it easy for developers to intuit the answers to questions such as:

1. What does a type actually consist of?
2. How should a type be constructed?
3. What purpose does a group of members serve?

Additionally, good code organization aims to make it easy to move code between files, and between lexical scopes in the same file.


### Layout sections

**Layout sections** appear in layout files, and contain all of the stored properties of a type, and a handful of designated memberwise initializers. They look like this:

```swift
extension Foo {
    struct Baz {
        let id: Int
        let name: String
        var data: [UInt8]

        init(id: Int) {
            self.id = id
            self.name = "<untitled>"
            self.data = []
        }

        init(id: Int, name: String, data: [UInt8]) {
            precondition(!name.isEmpty)

            self.id = id
            self.name = name
            self.data = data
        }
    }
}
```

Layout sections for enums contain only the enum cases. Noncopyable enums may additionally host `deinit` in their layout sections, since that is the only place they can be defined.

Layout sections for structs never contain anything except for stored properties and memberwise initializers. Noncopyable structs may also contain `deinit` in the layout section. (Classes may additionally contain overriding members in the layout section, due to the constraints of the language.)

All of the memberwise initializers that appear in a layout section use direct property assignment in their bodies — they never delegate to other initializers. Moreover, these are the *only* places where direct property initialization is permitted.

Prefer limiting the number of memberwise initializers when possible — the ideal layout section contains a single memberwise initializer that initializes all stored properties.

The memberwise initializers in the layout section are empowered to enforce *invariants* on the immutable (`let`) fields of a type.


### Constructor sections

**Constructor sections** contain `init`s, static constructor functions, and static factory properties. They look like this:

```swift
extension Foo.Baz {
    init(id: Int, name: (first: String, last: String)) {
        self.init(id: id, name: "\(name.first) \(name.last)", data: [])
    }

    static var admin: Self { .init(id: 0) }
}
```

Direct property assignment is prohibited in constructor sections. All constructors should delegate to a memberwise initializer. Adherence to this principle makes the enforcement of invariants within the memberwise initializer(s) meaningful.


### Conformance sections

**Conformance sections** contain witnesses for protocol conformances. They look like this:

```swift
extension Foo.Bar: Comparable {
    static func < (a: Self, b: Self) -> Bool { a.id < b.id }
}
```

Conformance sections are “good” places for members to live; it is preferable to organize members into conformance sections.

If a protocol conformance implies a conformance to a more general protocol, and some of the members in the conformance section for the refining protocol witness requirements for the more general protocol, then a second conformance section should be created for the more general protocol, and the members should be moved into that section instead.

```swift
// even though it is valid to place `description` in the `LosslessStringConvertible` block, it
// is better for it to get its own conformance section.
extension Foo.Bar: CustomStringConvertible {
    var description: String { "" }
}
extension Foo.Bar: LosslessStringConvertible {
    init?(_ description: String) { }
}
```

In rare situations, the same member might witness requirements for multiple unrelated protocols. One common scenario is a keynum that witnesses an associated type requirement shared by a serialization protocol and a deserialization protocol. In this situation, the shared witness should be moved to a third extension block, with no associated conformance.

```swift
extension Foo.Bar {
    enum QuxKey: String {
        case id
        case name
        case data
    }
}
extension Foo.Bar: QuxEncodable {}
extension Foo.Bar: QuxDecodable {}
```

### Name qualification

It may seem odd for name qualification to appear under a section about code organization, but in Swift, qualification is in fact downstream of code organization! The most important concept to be aware of is that the layout section behaves differently from all other sections, because names in a layout section are implicitly resolved against both the primary type *and* the parent type’s namespace, while names in other sections are only resolved against the primary type’s namespace.

This means that code in extension blocks can be easily moved to and from other extension blocks without respelling names, but code cannot be moved into or out of a layout section in the general case without adding or removing qualification. This is why we encourage keeping the layout section as small as possible.

As a rule, names should always be spelled with the minimal amount of qualification necessary to make the code compile. Moreover, `Self` should always be used to refer to the primary type in a file unless covariance forbids it.

Module qualification is discouraged in idiomatic Swift code.


### Where helpers go

A helper that only inspects its argument, to answer a question about that argument, belongs to the argument’s type, not to the type that happens to call it. Make it a member in an extension on the argument’s type (in that type’s layout file, or its extension file if the type comes from another module). Otherwise, coordinator types such as checkers, visitors and formatters turn into dumping grounds for functions that have nothing to do with their state.

```swift
// good — the question is about the hyperlink, so the hyperlink answers it
// the callers read fluently, for example: `link.points(to: domain)`
extension Hyperlink {
    func points(to domain: Domain) -> Bool {}
}

// bad — `NodeVisitor` holds the function, but nothing in it uses the visitor’s state
// the callers look awkward, for example: `self.doesPointToDomain(link: link, to: domain)`
extension NodeVisitor {
    func doesPointToDomain(link: Hyperlink, to domain: Domain) -> Bool {}
}
```

A helper that does belong to a coordinator’s domain, but never reads or writes `self`, should be a `static func`. That way, the signature shows that calling it can’t depend on, or change, the state of a pass in progress. Keep instance methods for the code that reads or mutates instance state, so that a reader can assume every instance method does.

```swift
// good — we assume that percent-encoding in this context is tied closely enough to `URI` that
// it would make sense to scope it under `URI`’s namespace, and it doesn’t depend on the state
// of any particular instance of `URI`, so a static function is appropriate
extension URI {
    private static func escape(unencoded: String) -> String {}
}

// bad — looks like it depends on the URI instance’s state, but doesn’t
extension URI {
    private func escape(unencoded: String) -> String {}
}
```


## Writing code

In general, we believe in the principle that code is edited far more often than it is written, and that code is read far more often than it is edited. So we prioritize ease of reading, editing, and writing, in that order. In particular, navigating counts as reading, so we always prioritize keeping code navigable over simply making code fast to write or generate.

### Type annotations

Type annotations should always appear in any position where they are supported in the Swift language. Type annotations make it easier to read code and gather assumptions, and reduce the amount of context needed to understand a snippet you haven’t worked on in a while. They also provide a handy audit trail when making changes to code.

```swift
let (name, age): (String, Int) = ("Alice", 30)
let list: [String] = ["a", "b", "c"]
for item: String in list {}
```

#### Initializer calls

Initializer calls should always be written with the explicit `init` tokens. There are several reasons why we do this. First, it reduces the temptation to omit type annotations, as `init` may be used with leading dot syntax, allowing one to write the following:

```swift
let foo: [Int] = .init(values)
```

instead of this:

```swift
// bad! don’t do this! here, the developer was likely tempted to remove the `[Int]` type
// annotation, because `[Int]` already appears nearby in the `[Int](values)` expression
let foo = [Int](values)
```

We always want references to types to live in syntactical positions where there is zero ambiguity as to whether the token refers to a type, or an expression.

```swift
// good — there is no ambiguity that `stat` is a type
let foo: stat = .init()
// bad — sourcekit-lsp context is needed in order to deduce that `stat` is a type
let foo = stat()
```

A second reason why we like `init` is navigational — if one writes `Foo(bar)`, it is not possible to Ctrl-click the `Foo` token and jump to the initializer being called, as the developer will be forced to break flow and clarify whether she wishes to travel to the primary type definition of `Foo` or the initializer. However, `Foo.init(bar)` provides clickable areas for each definition the developer might wish to jump to. As an AI coding agent, you might also experience the same friction when running sourcekit-lsp queries, and find `init` tokens useful for the same reasons.


#### Type conversions within complex expressions

The `.init` spelling, with leading dot syntax, is a powerful tool but can also make code difficult to read in complex expressions. It can also mask unwanted same-type conversions between numeric types, such as redundant `Int`-to-`Int` or `Double`-to-`Double` conversions.

In general, `init` should be written without leading type qualification if it would be clear to a user familiar with the API what the type conversion taking place is.

```swift
// here, we do not need to qualify with `Markdown.init(parsing: utf8)`, because a user familiar
// with the hypothetical API here would know what `init(parsing:)` is calling.
let document: Document = .init(markdown: .init(parsing: utf8))
```

Leading type qualification should be used if there are many possibilities as to what `init`s are being called, such as in complex arithmetic expressions.

```swift
// The `Double.init(z)` makes it crystal clear that two `Double`s are being added, and that no
// “weird” heterogeneous arithmetic is taking place here. Note that this example is actually
// unambiguous, and would compile without `Double` qualification, but this isn’t immediately
// obvious in the thicket of generic standard library numerical APIs.
let result: Double = x + Double.init(z)
```

#### Prohibition of SE-0213 (“Literal initialization via coercion”)

Do not use [literal coercion via implicit initializer invocation](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0213-literal-init-via-coercion.md), under any circumstances.

Literal coercion via implicit initializer invocation is special carve-out to the usual typechecking behavior of the compiler, which affects expression such as this:

```swift
let bytes: [UInt8] = try Path("Public/rules.ion").read()
//                       ^~~~
// implicit initializer call affects the inferred type of the argument!
```

Although this looks like a call to `Path.init(_: String)`, it will in fact be resolved to `Path.init(_: Path)` if such an overload exists at build time, and `Path` conforms to `ExpressibleByStringLiteral`. Incredibly, the behavior will *change* depending on whether `Path` is spelled with an explicit `init` token, as this disables literal coercion.

SE-0213 was originally (and shortsightedly) bolted onto the language to alleviate a common beginner stumbling block when writing overflowing literal expressions such as `UInt64(0xffff_ffff_ffff_ffff)`. However, it is always better to spell such expressions as `(0xffff_ffff_ffff_ffff as UInt64)`.

```swift
// good — the type context is provided by the type annotation, which is the best source of type context
let x: UInt64 = 0xffff_ffff_ffff_ffff

// okay — usually we would refactor this to avoid the awkward `as`, but this is still significantly
// better than literal coercion via implicit initializer invocation
let x: UInt64 = (0xffff_ffff_ffff_ffff as UInt64) &+ 1

// bad — avoid SE-0213 like the plague, and in this situation, insertion of the `init` token will surface
// the problem as a compiler error
let x: UInt64 = UInt64(0xffff_ffff_ffff_ffff) &+ 1
```

Because SE-0213 only goes into effect when the interstitial `init` token is omitted, it can be incredibly difficult to determine whether literal coercion is taking place, even with the assistance of sourcekit-lsp, as there is no physical token to run a semantic query against. As such, it constitutes an additional systemic motivation for mandating the explicit spelling of `init` everywhere.


### Explicit `self`

When writing instance members, always refer to other instance members with explicit `self`. Although `self` is not a “type annotation”, it serves a similar purpose when scanning code, as it greatly reduces the cognitive burden and context needed to understand a particular snippet of code.

```swift
// always say `self` if the thing being referenced is an instance member
let foo: Int = self.bar
```

Similarly, static members should be referred to with explicit `Self` (for enum, struct, or protocol members), or the name of the type (for class members).

In the future, we plan to have an IndexStoreDB–powered formatter that will enforce this rule automatically. But for now, it is your responsibility as a coding agent to ensure that instance member references are always qualified with `self`.


### Naming

Naming is a famously challenging skill for developers of all experience levels, and as an AI coding agent, choosing good names will make it much less likely that your human teammate will recoil in disgust at the code you have worked to provide.


#### Prefer full words, or single letters

Prefer spelling out complete words, unless the abbreviation is a common standalone term of art, like “*min*” or “*max*”. Avoid abbreviating variable or function names. Always spell out abbreviated compound words.

Omit suffixes like `-Value` that add no clarity, or are redundant in the context of static type information.

Default to single letters like `i` for indices, unless a longer name would provide meaningful clarity.

```swift
// `j` is just a marker, a longer name would provide no clarity
let j: String.Index = string.index(after: i)
// `colon` points to a `:` character, so we name this index variable `colon`
let colon: String.Index? = string.firstIndex(of: ":")
```

The following are examples of good names:

| good example | notes |
| --- | --- |
| `probability` | — |
| `frequency` | — |
| `relativeError` | not “relError” |
| `i` | use this as a throwaway counter variable, such as an index |
| `max` | “max” is acceptable, and preferred over “maximum”, as it’s a term of art, despite being an abbreviation |

The following are examples of bad names to avoid:

| bad example | notes |
| --- | --- |
| `prob` | — |
| `freq` | — |
| `relError` | — |
| `tempFoo` | say `temporaryFoo`, or just `temporary` |
| `numItems` | say `items` or `itemCount` |
| `avgVal` | just say `average`, don’t say “Val” — everything is a value! |
| `newValue` | just say `new` — again, everything is a value, so “Value” adds nothing! |
| `sizeInt` | just say `size` — the -`Int` suffix is redundant if we are using type annotations well |


#### Let mathematics read like mathematics

Default to single letters like `x` if reproducing well-known mathematical formulae.

```swift
// good — everyone remembers “a squared plus b squared equals c squared” from grade school
let c: Double = .sqrt(a * a + b * b)

// bad — this is verbosity that obfuscates, rather than clarifies, the underlying math
let hypotenuse: Double = .sqrt(sideOne * sideOne + sideTwo * sideTwo)
```

Use proper mathematical symbols for well-known concepts.

| good example | notes |
| --- | --- |
| `μ` | mean |
| `σ` | standard deviation |

| bad example | notes |
| --- | --- |
| `mean` | not that “bad” depending on context, but in a formula, `μ` is just better |
| `stdDev` | bad for multiple reasons, as previously discussed |


#### Boolean flags

As a general rule, `is`- or `has`-prefixed variable names should be considered a code smell. This might be unintuitive to those accustomed to other style guides, but the Swift language has features that provide superior alternatives in almost all situations.

Use optionals to directly model presence flags, by tying the indication of presence to the actual presence of a value.

```swift
// good — use the state of the optional to directly model the presence of the property!
// avoid “sugaring” struct properties by adding a computed “hasFoo” or “isFoo” property,
// instead check at the call site using `if case _? = $0.bio` or `if case nil = $0.bio`.
struct Profile {
    var bio: String?
}
// bad — if you see a `foo` paired with a `isFoo` or `hasFoo` property, refactor it.
struct Profile {
    var hasBio: Bool
    var bio: String
}
```

If a flag truly has no associated value, omit the prefix too, as this makes it easier to upgrade the field to an enum or introduce an associated value later, which happens quite frequently.

```swift
// good — if verification later turns out to be more complex than a boolean, we can swap out
// the `Bool` with an enum or a value
struct User {
  var verified: Bool
}

// bad — what if we want to add the date of verification later?
struct User {
  var isVerified: Bool
}
```

The main exception to this rule is witnesses to protocols that declare `is`- or `has`-prefixed requirements. A common example is ``Collection.isEmpty``. Don’t vend `empty` as a property forwarded by an `isEmpty` shim just to satisfy the protocol; just implement `isEmpty` directly. This only applies to standard library protocols. For APIs we design ourselves, avoid `is`- and `has`-prefixed names entirely.

#### Boolean case indicators

If you have an enum that you want to sugar with **case indicators**, use the same base names for the indicators as the cases themselves.

```swift
enum Access {
    case vip(grandfathered: Bool)
    case standard
}
extension Access {
    // good — the indicator property is named after the case
    var vip: Bool {
        switch self {
        case .vip(grandfathered: _): true
        default: false
        }
    }

    // bad — don’t perform a natural-language lettercasing transformation
    // on something that is permanently tied to another API
    var isVIP: Bool {
        switch self {
        case .vip(grandfathered: _): true
        default: false
        }
    }
}
```

Case indicators are most motivating on enums. They should be rare on structs — they won’t usually compile without a name permutation (as they would shadow a stored property name), and they rarely provide enough API value over caller-side pattern matching to justify their inclusion. If you do choose to add a case indicator to a struct, suffix it with -`Present` or -`Enabled` instead of prefixing it with `has`- or `is`-.

For a struct field indicator to be motivating, the use case should generally involve:

- an underlying field type that would otherwise need a viral ``Equatable`` if `==(_:_:)` were to be called on it, and
- lots of callers (such as ``Sequence.filter(where:)`` predicates) that would be burdened by repeated use of language-level pattern matching.

#### Avoid `lhs` and `rhs`

The names `lhs` and `rhs` are terrible parameter names, and should never be used. Use `a` and `b` in binary operator signatures instead, or choose more descriptive names (discussed in the next subsection) if appropriate.

```swift
static func < (a: Self, b: Self) -> Bool { a.rawValue < b.rawValue }
```

Please note that the names `lhs` and `rhs` are prescribed by the Apple Swift style guide — that style guide is wrong, and you shouldn’t listen to it.


#### Shadowing `self`

Shadow the `self` keyword if something is semantically an instance method, but cannot be expressed as such due to the constraints of the language. Common examples include operator declarations.

```swift
// good — this would be a `mutating` instance func if it weren’t an operator
static func += (self: inout Self, next: Self) {}

// bad — the “left-hand” aspect of the `inout` parameter is the least interesting
// thing about it! same with the second parameter.
static func += (lhs: inout Self, rhs: Self) {}
```

When switching on `enum` variants with payloads, shadow `self` if you are conceptually switching on cases of `self`.

```swift
// good, if the enum wrapper is a performance shim we are using to avoid heavyweight
// existentials or subclassing, we don’t want to think about the wrapper when writing
// a simple manual method dispatch
switch self {
case .bool(let self): self.encode(to: &encoder)
case .int(let self): self.encode(to: &encoder)
case .float(let self): self.encode(to: &encoder)
}

// bad — this is likely obscuring what all three cases have in common.
switch self {
case .bool(let bool): ...
case .int(let int): ...
case .float(let float): ...
}
```

But only do this for variant-like enums.

```swift
// good — we should be thinking about the relationship between the `id` and the `value`.
switch self {
case .foo(id: let id, let value): ...
}

// bad — treating the `id` as the new conceptual `self` is a bridge too far.
switch self {
case .foo(id: let self, let value): ...
}
```


#### Shadowing variable bindings

Shadow local variable bindings if the rules of the language allow it and the old value is no longer needed, or redundant with data stored in the new value.

Aggressive shadowing will make it easier to reason about code, by reducing the number of independent values in scope at a given time. Historically, it was discouraged because it reduces the effectiveness of grep search. However with modern sourcekit-lsp tooling (which is available to you), the shadowing tradeoff is highly advantageous.

```swift
// good — the old `tile` is no longer needed in this scope, and the `TileSnapshot` value likely
// already contains a copy of the id, if it were needed
for tile: TileID in tiles {
    if  let tile: TileSnapshot = cache.tiles[tile] {
        gdp += tile.z.stats.gdp
    }
}

// bad — `tileID` and `tileSnap` are terrible names, as previously discussed, and they are also
// totally unnecessary.
for tileID: TileID in tiles {
    if  let tileSnap: TileSnapshot = cache.tiles[tileID] {
        gdp += tileSnap.z.stats.gdp
    }
}
```

As illustrated in the example, aggressive shadowing also has the perk of rendering many thorny naming debates moot.

#### Closure parameters

Shorthand closure argument names (`$0`, `$1`) are good, use them for simple closures. You should only start naming closure parameters if closures are very large (>50 lines), if they include nested closures where you need to disambiguate outer parameters, or if the closure logic becomes significantly more readable with named parameters.

If you decide to name a closure parameter, always include a type annotation. It’s okay to omit the return type, if type inference allows for it.

```swift
// good — these are clear and recognizable patterns
let sum: Double = values.reduce(0, +)
let squares: Double = values.reduce(0) { $0 + $1 * $1 }

// bad — the ceremonious names harm pattern recognition. also, they’re missing type annotations!
let sum: Double = values.reduce(0) { accumulator, value in accumulator + value }
let squares: Double = values.reduce(0) { (accumulator, value) in accumulator + value * value }
```

When a closure receives a tuple as its single argument, prefer splatting the tuple elements into separate shorthand arguments (`$0`, `$1`, `$2`, etc.) rather than accessing tuple members (`$0.0`, `$0.1`, `$0.2`, etc.).

```swift
// good — splat tuple elements into $0, $1, $2
let result: [(Int, Double)] = enumerated.map {
    ($0, $1 * 2) // $0 is index, $1 is value
}
// good — another example
let histogram: [(Double, Double)] = items.enumerated().map {
    let midpoint: Double = range.min + (Double.init($0) + 0.5) * width
    return (midpoint: midpoint, count: $1)
}
```

#### Grouping variables with tuples

Tuples are one of Swift’s finest features, use them freely! Consider grouping related variables using tuples with named elements instead of separate variables.

```swift
// good — these values go together, in fact, the author is probably intending to assemble a
// `Range` out of them!
let range: (min: Int64, max: Int64) = (
    min: .init(expected.μ - 3 * Double.sqrt(expected.σ²)),
    max: .init(expected.μ + 3 * Double.sqrt(expected.σ²))
)

// bad — we are using suffixes to indicate something that could have been modeled structurally
let minRange: Int64 = .init(expected.μ - 3 * Double.sqrt(expected.σ²))
let maxRange: Int64 = .init(expected.μ + 3 * Double.sqrt(expected.σ²))
```


### Destructuring patterns

**Destructuring patterns** are language-level patterns that extract payloads from tuples, optionals, and enums.

#### Destructuring optionals

Always prefer destructuring optionals using the `?` operator. Avoid spelling `.some` or `.none` with their named constructors.

```swift
let x: ()?? = nil

// good — uses postfix `?`
switch x {
case _??:
    print("inner optional is inhabited")
case nil?:
    print("outer optional is inhabited with nil")
case nil:
    print("outer optional is nil")
}
// bad — avoid spelling `.some` or `.none`
switch x {
case .some(.some):
    print("inner optional is inhabited")
case .some(.none):
    print("outer optional is inhabited with nil")
case .none:
    print("outer optional is nil")
}
```

#### Checking for equality

In Swift, `==(_:_:)` has a specific meaning, and it is rarely what you want.

When checking if an instance of an enum is a particular case, always prefer matching with `case`, never with `==`.

```swift
// good — matches on `case`, does not pollute the API with `Equatable` references
if  case .foo = bar {}
// bad — evaluates `==(_:_:)`, which tempts developers into spraying `Equatable` everywhere!
if  bar == .foo {}
```

If the value being destructured is optional, always make the destructuring stricter, to expect the optional type:

```swift
// good — this will only ever match a truly optional `baz`
if  case .foo? = baz {}
// bad — it is missing an important static typing hint
if  case .foo = baz {}
```

Keep in mind, however, that `case` provides no benefit over `==` for expressions that perform no destructuring and simply wrap a call to `==(_:_:)` via `~=`. You don’t need to rewrite `==` comparisons as `case` patterns unless `case` is contributing a genuine destructuring operation to the comparison.

```swift
let x: Int?
let y: Int
let magic: Int = 13
// good — this does call `Int.==(_:_:)`, but it avoids calling `==(_:_:)` on `Optional`,
// so the `case` pattern is well-motivated
if  case magic? = x {}

// unnecessary if `y` is non-optional, this is merely disguising an `Equatable.==(_:_:)`
// call with more-innocuous syntax. If `y` were optional, this should instead be written
// as `case magic?`, with the trailing `?`
if  case magic = y {}
```

Rigorous adherence to `case`-based destructuring and pattern matching will help limit the number of `Equatable` conformances that must be virally propogated everywhere, which helps keep APIs lean and free of unnecessary conformances.


#### Comparing several fields

To compare several fields at once, compare tuples instead of chaining `==` with `&&`. The tuple lines the fields up, so a missing or mismatched field is visible at a glance.

```swift
// good
static func == (a: Self, b: Self) -> Bool { (a.scope, a.last) == (b.scope, b.last) }

// bad
static func == (a: Self, b: Self) -> Bool { a.scope == b.scope && a.last == b.last }
```

This is especially useful for writing ``Comparable`` conformances, which tend to be gnarly when written out using manual field-by-field comparison logic.


### Conditions

Separate the conditions of an `if`, `guard` or `while` with commas, not `&&`. Each comma-separated condition can be a binding or a pattern, gets its own line, and can be reordered or deleted without rebalancing an expression. Likewise, merge an `if` nested directly inside another `if` (with no `else` on either) into a single statement.

```swift
// good
if  arguments.contains("deprecated"),
    self.name != "main.swift" {
    return true
}

// bad — one condition is buried in an expression, and the other in a nested `if`
if  arguments.contains("deprecated") {
    if !self.name.isEmpty && self.name != "main.swift" {
        return true
    }
}
```

`&&` is still correct inside an expression whose value you store or return, such as `let ready: Bool = a && b`.


### Functional patterns

The `reduce(into:_:)` method is your friend, use it to return the result of a loop that would otherwise have to mutate bindings declared in the outer scope.
For accumulations that don’t mutate collections, you can also use an ordinary `reduce(_:_:)`.

```swift
// good — `frequency` will never be mutated after this loop, and a `var` binding would sacrifice
// that guarantee. using `reduce` here enables us to preserve immutability
let frequency: Double = (k.min ... k.max).reduce(into: 0) {
    let count: Int = histogram[$1, default: 0]
    let frequency: Double = Double.init(count) / Double.init(samples)
    $0 = max($0, frequency)
}
```


### String processing

Most Swift code in the wild processes strings by counting characters, which is the main reason this section exists. Counting is the habit to unlearn: an index should come from a search, a standard library method, or a regex match. An offset counted from the length of a literal is only acceptable when the characters it skips are checked against that literal right where it is used.


#### Slice from indices you found or checked

```swift
// good — the index comes from a search, so it is correct for any input
if  let dot: String.Index = name.lastIndex(of: ".") {
    let stem: Substring = name[..<dot]
}

// bad — `-6` is the length of “.swift”, counted by hand; it is wrong for any other extension,
// and nothing ties it to the literal it was counted from
let stem: Substring = name[..<name.index(name.endIndex, offsetBy: -6)]
```

The ban covers every disguise of the same arithmetic, including `offsetBy: "foo".count`, `dropFirst(14)` and `prefix(2)`, unless the skipped characters are checked on the spot, as the `offsetBy: 3` below is.

Consuming prefixes and suffixes is usually not the best way to slice a string. Lots of trimming-heavy code becomes significantly cleaner when refactored into index-based alternatives.

```swift
// good — error handling comes out naturally with the colon index on hand
if  let colon: String.Index = uri.firstIndex(of: ":") {
    guard uri[..<colon] == "https" else {
        throw UnsupportedLink.scheme(uri[..<colon])
    }

    // the constant `3` is okay here, because that refers to a fixed-width delimiter `://`
    guard
    let domain: String.Index = uri.index(colon, offsetBy: 3, limitedBy: uri.endIndex),
    // we could have elided an always-true check by taking the `index(after:)` of the colon,
    // at the cost of an additional variable binding. if the code cares about the position
    // immediately after the colon, that might be worth it
    uri[colon ..< domain] == "://" else {
        throw UnsupportedLink.malformed(uri)
    }
}

// bad — if you then drop the prefix, you have to count again.
// if the delimiter is a literal, count it once (in the guard)
if  uri.starts(with: "https://") {
    let domain: Substring = uri.dropFirst(8)
}
```

The good example above is longer than the bad one, which is why people are often tempted to write the bad one instead. But the good one is clearer, potentially faster, and gives you error handling for free.


In situations where a prefix is tested for, but never used, prefer `starts(with:)` over `hasPrefix(_:)`. The standard library has no `ends(with:)`, so `hasSuffix(_:)` remains the way to test for a suffix. These are relatively rare situations, since often if you are checking whether a string starts or ends with something, you also want to use that slice.


#### Test single characters with patterns

```swift
// good — destructures the optional, as described under “Destructuring optionals”
if  case "."? = name.first {}

// bad — a string comparison standing in for a character test
if  name.hasPrefix(".") {}
```


#### Use `Character` properties instead of listing characters

A hand-written list of characters is almost always incomplete. Unicode has more whitespace than space, tab and carriage return.

```swift
// good
let trimmed: Substring = line.drop(while: \.isWhitespace)

// bad — misses U+000B, U+00A0, U+2028, and many more
let trimmed: Substring = line.drop { $0 == " " || $0 == "\t" || $0 == "\r" }
```

#### Use hex literals for ASCII values

Avoid using Unicode properties when the property is wider than what you mean. For example, `isWholeNumber` accepts non-ASCII digits such as ‘٣’. If a pattern only applies to ASCII characters, drop down to `utf8` views and match on integer literals.

Write ASCII values in hex, never decimal. When writing ASCII values, always include a comment nearby identifying the characters they represent.

```swift
// good
let id: String.Index? = line.utf8.firstIndex {
    // '0' ... '9'
    0x30 ... 0x39 ~= $0 ||
    // 'a' ... 'f'
    0x61 ... 0x66 ~= $0 ||
    // 'A' ... 'F'
    0x41 ... 0x46 ~= $0
}

// bad — `isHexDigit` accepts fullwidth compatibility forms, which may not be spec-compliant
let id: String.Index? = line.firstIndex(where: \.isHexDigit)
```

Drop down to the UTF-8 level only when the domain calls for it, or in performance-critical contexts. In most situations, performing the equivalent operations on the default `Character` view (such as searching for a delimiter) is fine, and more readable.


#### Regular expressions

Use a `Regex` to match a short string against a grammar once, such as a file name or a version string. The regex states the grammar in one place, while hand-written parsing restates it as control flow that has to be read line by line to recover the format.

```swift
// good — the grammar is visible, and the capture is the version
let manifest: Regex<(Substring, Substring)> = /Package@swift-(\d+(?:\.\d+){0,2})\.swift/
if  let match: Regex<(Substring, Substring)>.Match = name.wholeMatch(of: manifest) {
    let version: Substring = match.1
}

// bad — the same grammar, rebuilt from offsets, `split` and digit checks
guard
name.hasPrefix("Package@swift-"),
name.hasSuffix(".swift") else {
    return false
}

let start: String.Index = name.index(name.startIndex, offsetBy: 14)
let end: String.Index = name.index(name.endIndex, offsetBy: -6)
let version: Substring = name[start ..< end]
let parts: [Substring] = version.split(separator: ".", omittingEmptySubsequences: false)
```

#### Pipelines and slicing loops

In hot paths, such as code that runs once per token or once per line of a large file, prefer a slicing loop. Avoid both regexes and chains of allocating collection operations there, because each stage of `split`, `map` and `joined` allocates an intermediate buffer.

```swift
// good — no intermediate arrays; every index comes from a search
var scope: String = ""
var remainder: Substring = raw
while let dot: String.Index = remainder.firstIndex(of: ".") {
    scope += Self.unencase(remainder[..<dot])
    scope += "."
    remainder = remainder[remainder.index(after: dot)...]
}
scope += Self.unencase(remainder)

// bad in a hot path — allocates an array of `Substring`, an array of `String`, and the result
let scope: String = raw.split(separator: ".").map { Self.unencase($0) }.joined(separator: ".")
```

Outside hot paths, pipelines are fine, but can sometimes be a code smell that suggests an expression is “doing too much” and could be broken down. When pipelines do appear, consider if a `lazy` view might eliminate intermediate buffers. (`lazy` helps `map`, `filter` and `joined`, but `split` always returns an array.)


#### Interpolate instead of calling `description`

A `description` property witnesses `CustomStringConvertible`; it is not a conversion API. Interpolate the value instead.

```swift
// good
let target: String = "\(primaryType)"

// bad
let target: String = primaryType.description
```


### Constants

When defining constants, prefer `static var` computed properties over `static let` properties. If constants are being accessed across module boundaries, the computed property should be `@inlinable`, not `@usableFromInline`, to facilitate constant folding.

```swift
// good — this is, in many ways, easier for the compiler to optimize than a stored `let`
@inlinable static var mask: UInt32 { 0xff000000 }

// bad — this introduces avoidable lazy initialization and thread safety concerns, and
// is often harder to optimize, particularly across module boundaries
@usableFromInline static let mask: UInt32 = 0xff000000
```

In idiomatic Swift code, `static let`s have few motivating use cases that aren’t better-served by `static` computed properties. Contrary to beginner intuition, `static` computed properties are often more concurrency- and optimizer-friendly than their stored counterparts, and defaulting to them will help you avoid falling down maddening `Sendable` rabbit holes.


### Editing code

You are not the only person working on the code you are given. Try to avoid destroying scaffolding that other people are using to make code easier to edit.

#### Don’t wipe your teammates’ comments

Assume that code comments you encounter were left there for a reason, don’t just wipe them for no reason. Only delete code comments if they are clearly wrong or out-of-date, and always notify your human partner if you do choose to delete comments.

#### Don’t wipe trailing commas

Similarly, please avoid deleting multiline trailing commas — they make multiline expressions easier to edit, and removing them proactively makes diffs noisier.


## Writing tests

Unit tests should always use the modern Swift Testing framework. XCTest should never be used.

Avoid `@testable` in finalized production code — it is okay for experimentation and iteration, but should be removed before libraries are considered release-ready.

### Test suites

Tests should be organized into **suites**, which look like this:

```swift
// Parsing.swift
import Testing

@Suite struct Parsing {}
```

Suite names are generally nouns, and should not end in the word `Test`. (You may encounter legacy code that uses the -`Test` suffix; it is okay to keep the suffix when modifying existing tests, but avoid using it for new tests.)


### Test functions

The ideal **test function** is a `static func`; upgrade to an instance method only if the test requires context that involves initializing an instance of the suite. One reason to upgrade to instance methods is to reduce setup burden, by factoring out a shared preamble into the suite’s initializer.

The names of test functions should almost always begin with a capital letter. This is a special naming convention specific to test functions. Test function names should not be prefixed or suffixed with the word `test`, as this would be redundant with the `@Test` attribute.

If capitalizing the name of a test function would conflict with a type name, rename the test function; do not start using module qualification. One technique for dealing with this situation is to rename the test function from a singular noun to a plural noun. For example, you might rename a test that exercises floating point logic from `Float()` to `Floats()` to avoid shadowing the standard library type.

A rare exception to the capital letter rule is proper nouns and trademarks — for example, the name of the famous Apple device should always be spelled `iPhone`, never `IPhone`.


### Test sections

It is natural to wonder if test suites should be organized into layout, constructor, and conformance sections, similar to the way that library code is organized. The answer is no, although similar principles apply.

If a test suite has no stored properties and no `init`, all test functions should be placed in the primary type definition.

If a test suite has an `init`, or stored properties, then the test functions should go in a separate extension block.

Test helpers, including static properties, always go in separate extension blocks, at the end of a file.


### Asserting behaviors

There are many ways to write the same test, but some patterns are more fluent than others. In particular, using the right patterns can help reduce the number of instances of `Issue.record` that appear in a test case.

#### Using `#require`

The `#require` macro can be used to unwrap optionals. However, direct comparison via optional-chaining is often more concise, and preferred when possible.

```swift
#expect(parsed?.count == expected)
```

#### Extracting case payloads

Use optionals to store extracted enum case payloads, and run comparisons against the optional values.

```swift
let value: UInt64?
if  case .uint64(let uint64)? = magnitude {
    value = uint64
} else {
    value = nil
}

#expect(value == expected)
```

#### Binding thrown errors

When a test needs to inspect a thrown error, bind it with `try #require(throws:)`, which returns the error as a non-optional value. Do not bind the result of `#expect(throws:)`, which is optional. A test where nothing is thrown then reports one failure instead of two, and the error can be interpolated directly instead of reaching for `.description`.

```swift
let error: ParsingError = try #require(throws: ParsingError.self) {
    try Version.init(parsing: "1.x")
}
#expect("\(error)" == "invalid component 'x'")
```

Use `#expect(throws:)` only when the error itself is not inspected, which is sometimes the case when one test makes several independent throw checks that should all be reported.


## Preparing work for review

The rules in this guide are only useful if you remember them while you write. Don’t just read this guide at the start of a session and then fall back on the patterns that dominate public Swift code as the session progresses.

### Style is everyone’s responsibility

A context compaction keeps the instruction to follow this guide, but drops its rules. Because people tend to mimic the patterns in the code around the code they are editing, unidiomatic code tends to beget more unidiomatic code.

So before each commit, re-read the sections of this guide that the commit’s diff touches, and review that diff against them as a style reviewer would. A commit is small enough to check this way; a whole branch at the end of the work is not. Re-read the sections after every compaction, too.

### Keep pull request descriptions up to date

Before you ask for review, or for another round, update the pull request description, so it describes the code as it now is, rather than how the first version worked.

### Address the patterns called out by review comments, not just the comments themselves

Treat each review comment as one example of a pattern, not as a single line to fix. Before you reply, search the whole branch for other instances of the same pattern, fix all of them, and say how many there were. If the pattern isn’t covered by this guide yet, say so, so that it can be added. If you keep persistent notes, record the correction as a rule you can apply next time, not as a note about this one pull request.


## Reviewing branches

Your human teammate may occasionally assign you code review responsibilities. Code review generally refers to three broad processes:

1. Architectural review
2. Cleanup and cultural circulation
3. Style guide compliance

You will usually be tasked with executing only one of these three procedures at a time — other team members will handle the others.

### Architectural review

**Architectural review** is exactly what it sounds like — coming at a set of code changes with fresh eyes, taking a step back, and assessing whether those changes were ever a good idea in the first place. Comb new systems for redundancies and assess whether historical fallbacks and migration aids are still needed in the present day. Be on the lookout for convoluted workarounds stemming from limitations of internal libraries we maintain — this often serves as a hint that a GitHub issue should be filed against one of those libraries.

Be bold and be picky — do not be afraid to send a PR back to the team for more work. The Queen will override you frequently, don’t be offended when this happens, as the motivation is to encourage you to criticize aggressively.

### Cleanup and cultural circulation

**Cleanup** refers to the compaction of code changes that may have been introduced as iterative aids during development, but are not needed or useful to achieve the essential goals of the task. Examples of cleanup include, but aren’t limited to:

- Removing spuriously introduced `Sendable`. This situation occurs frequently due to misleading Swift compiler diagnostics. Be especially vigilant against cargo-culted conformances — the vast majority of Swift training data in the world is of poor quality and teaches bad practices.
- Unnecessarily `public` API — downgrade `@frozen public` things to `@frozen @usableFromInline`, `@inlinable public` to `@inlinable`, et cetera.
- Low value API sugar — strive for expressive, composable APIs — don’t be afraid to ask your human for help brainstorming!

**Cultural circulation** is more nuanced. During the course of development, much logic will overlap or be implemented multiple times, and some of those implementations will be “better” than others. Cultural circulation refers to the sharing of best practices such that all use sites are following the best patterns. It often, but doesn’t always include refactoring duplicated logic into formalized APIs.

Cultural circulation is sometimes supplemented by insights from the architectural review phase — your teammate might forward you ideas for cultural circulation that were generated by the architectural reviewer.

### Formatting and style guide compliance

**Style guide compliance** is the most mechanical of the review phases. It is self explanatory — the task is to apply the contents of this style guide to all modified code. The main purpose of having this phase is to allow other team members to focus on their respective assignments, without having to penalize them for failing to adhere meticulously to the style guide. That said, following the style guide is *everyone’s* responsibility, other team members should never ignore the style guide under the assumption that the stylist will take care of it.

**Formatting** comes after style guide alignment, and it is always the last phase of review, as it is usually a waste of time to format midway through a sprint while code is still being edited. Formatting Swift code *should* be automated, and most projects use the [dollup](https://github.com/rarestype/dollup) formatter. That said, you should not proactively run `dollup` on code bases that were not already being diligently formatted. A good way to tell if a PR requires `dollup` is to check if the repository’s `Scripts/TestAll` hook contains a step that checks for `dollup` diffs. If it’s there, you should always run the formatter before concluding this review stage, as you can be certain that CI checks will fail otherwise.

Although this style guide is principally concerned with Swift code, you should also try to ensure that foreign language code (TypeScript, GitHub Actions YAML, etc.) you modify is also well-formatted. Because `dollup` is Swift-only, this usually just entails wrapping overlong lines to fit within a standard **96 character** page width. (Do not introduce new foreign language formatters.)

English language prose in markdown files is an exception to the general line length limit — paragraphs should flow without interior newlines. Inline code snippets within markdown files however, must still follow the standard 96 character line length limit.
